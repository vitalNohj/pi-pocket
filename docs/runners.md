# Sessions on another computer

As the server owner, you link a computer with a one-time code:

1. In Pi Pocket, go to Menu → **Access** → **Computer** → **Link a computer**. Enter a name, then choose **Get a link code**. The screen shows the server address and the code. The code works once and expires after 10 minutes.
2. Give them to the runner on that computer:
    - **With the Pi Pocket desktop app:** the app has the runner built in. In its settings, under **Runner**, enter the address and code, then choose **Link**. The app keeps the runner running while it is open.
    - **Any other computer:** install Node.js 22.19 or newer, then run:

        ```sh
        npm install -g pi-pocket-runner
        pi-pocket-runner
        ```

        `pi-pocket-runner` opens a menu: use the arrow keys and Enter. Choose **Link this computer**, enter the server address, such as `https://pocket.example.com`, then paste the code. The runner checks that Pi Pocket answers at that address and saves the link. Then choose **Start**, and leave the terminal open. Press Ctrl+C to stop the runner and its commands.

The runner is its own npm package, `pi-pocket-runner`. Where Pi Pocket is installed with its runner, `pi-pocket runner` does the same as `pi-pocket-runner`: use either. The commands below say `pi-pocket-runner`.

The server owner links computers, and so do the guests the owner lets (**Link runners** on their page in **Access**). A link code is worth its maker's permission to link at the moment it is used: when the owner takes that permission back, or removes the person, their open codes link nothing. Only link a server you trust: its session commands run as your user account on the linked computer.

**Wrong link codes.** The server counts wrong codes for each client address. Five wrong codes in 10 minutes lock that address out of linking for 10 minutes. The third lockout of an address bans it; its count starts over a week after its last lockout. A banned address gets the same answer as a wrong code. The ban stays until someone in charge of **This server** lifts it in **Access** → **Settings** → **Linking limits**, under **Banned from linking**. The address of this server's own machine is never banned, because every client of an unnamed proxy shares it.

Above that, a ceiling catches guessing from many changing addresses: 50 wrong codes in 10 minutes from all addresses together pause new linking for 10 minutes and void every open code. Linked computers and their keys are not affected. **Linking limits** says when an address or the whole server is locked, and why.

The server takes the client address from the connection. It believes a proxy's header only for its own proxy: Cloudflare's `CF-Connecting-IP` behind the Cloudflare tunnel, and Tailscale Serve's `X-Forwarded-For` behind Tailscale Serve, when `tailscale whois` names that address as a device of the tailnet. Both only for requests from this machine. Without a working `tailscale` command, no address counts as a tailnet device.

The computer connects out to the server over a WebSocket. It needs no open port, SSH, or provider key. Pi, its models, the provider keys, and session history stay on the server. Sessions read and write files and run commands, including git, on the linked computer.

## Secure link

The link has its own keys, like SSH, on top of HTTPS (`secure-link.ts`, in `packages/runner/src/` and `src/server/runner-link/`):

- The server has one key, made once and kept in its data folder. It does not change when the website certificate renews.
- Each computer makes its own key when it links. Its private key stays on that computer; the server keeps only its public key.
- The link code never travels. The runner proves it knows the code, and the server proves it knows the code too, so someone in the middle at link time cannot put in their own key.
- The runner keeps the server's key. On each connection, each side proves its key, and every message after that is encrypted and signed. A server without the key, even one with a valid certificate, is refused: the runner sends it nothing, says once "… did not prove it is the server this computer linked to", and tries again.
- Only the server the computer linked to can stop its runner for good, and it proves that each time: inside the encrypted link, or with a signed refusal when the computer was removed or linked again. An HTTP error, a close code, or another program at the server's address never stops a runner. It tries again.
- `pi-pocket-runner status` shows both keys' fingerprints. **Access** shows the server's where it makes the code, and each computer's on its page in **Settings**. They should match.

A computer linked by an older runner shows **Link again** in **Access** → **Settings**. It makes a code for that computer: link it with that code, and it keeps its sessions and people. Linking a computer again ends every connection of its old key, also one that was still connecting. Replacing the server's data folder makes a new server key: every computer must link again.

## Commands

Run these commands on the linked computer:

| Command                                                | What it does                                                                                                                                                                 |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pi-pocket-runner`                                     | In a terminal, opens a menu: start, run as a service, link again, unlink, and help.                                                                                          |
| `pi-pocket-runner start`                               | Runs with the saved link in this terminal or a program that runs the runner, such as the desktop app.                                                                        |
| `pi-pocket-runner link <server> <code> [--allow-http]` | Saves a link without questions. Use the server address and a one-time code from **Access**. See [Plain HTTP](#plain-http).                                                   |
| `pi-pocket-runner service [remove]`                    | Runs as a systemd user service on Linux, or starts at sign-in with a Windows scheduled task or macOS launch agent. `service remove` stops and removes it and keeps the link. |
| `pi-pocket-runner status`                              | Shows the saved link, both keys' fingerprints, and whether git and GitHub are ready. It does not check the connection.                                                       |
| `pi-pocket-runner unlink`                              | Deletes the saved link on this computer. Also unlink the computer in **Access** → **Settings** to stop it and cancel its key.                                                |

The runner asks nothing on the computer. Everything about who may use it, and where, is decided in Pi Pocket ([Who may use a computer](#who-may-use-a-computer)).

### A computer nobody sits at (Linux)

`pi-pocket-runner service` keeps the runner running as a systemd user service (`pi-pocket-runner.service`), for a computer such as a build server. Nobody needs to sit at the computer: approvals happen in Pi Pocket.

The service uses the Node.js, runner, link file, and `PATH` of the shell that installed it. Install the runner with npm first (`npm install -g pi-pocket-runner`): a copy in the npx cache is refused, because npm can clear it. Its log is in `journalctl --user -u pi-pocket-runner.service`. To keep it running while you are logged out, run `loginctl enable-linger $USER`. `pi-pocket-runner service remove` stops and removes it.

### Start at sign-in (Windows and macOS)

On Windows and macOS, `pi-pocket-runner service` starts the runner now and each time you sign in. These are per-user sign-in jobs, not system services: they do not run while you are signed out. A copy in the npx cache is refused on all three systems; install with `npm install -g pi-pocket-runner` first.

- **Windows:** installs the **Pi Pocket runner** scheduled task in Task Scheduler. It runs as the current user at log-on, without admin rights or a password. It uses the selected Node.js, runner, and link file, and starts in your home folder. The task can run on battery power, has no time limit, and retries failures up to 3 times, 1 minute apart. If Windows refuses registration, the command prints the PowerShell error and fails; it does not try another installation method. To check task history, open Task Scheduler → Task Scheduler Library → **Pi Pocket runner** → **History** (enable task history if needed). This history records task events; it does not save the runner's console output.
- **macOS:** writes `~/Library/LaunchAgents/dev.pi-pocket.runner.plist` and loads it into your signed-in GUI session. It uses the selected Node.js, runner, link file, and the current shell's `PATH`. Both output and errors go to `~/Library/Logs/pi-pocket-runner.log`. launchd restarts failures with a 10-second throttle. A runner stopped permanently by the server prints its message and exits with code 0 in macOS service mode so launchd does not restart it. Other modes and platforms keep exit code 3 for this.

`pi-pocket-runner status` names a running scheduled task or launch agent. The terminal menu names the same mechanism. `pi-pocket-runner service remove` stops and removes the scheduled task or launch agent, but keeps the saved link.

For scripts, use `pi-pocket-runner link <server> <code>`, then `pi-pocket-runner start`.

The link file is `~/.pi-pocket/runner.json`. It contains this computer's key, and only your user account can read it. Do not share it. Use `--config FILE` or `PI_POCKET_RUNNER_CONFIG` to choose another file; `--config` takes priority. `PI_POCKET_RUNNER_DAEMON` selects a pi-env daemon instead of the packaged one.

Run `pi-pocket-runner` again to start, change, or replace a saved link. Deleting the link file alone does not stop a runner that is already running.

**Where a build comes from.** **Access** → **Computer** → **Link a computer** shows the install command for the runner's version that this Pi Pocket pins, from npm (`npm install -g pi-pocket-runner@<version>`). Each release also has the runner's tarball, which the `Runner` workflow attaches to it. A server that offers another build sets `PI_POCKET_RUNNER_PACKAGE`, for example to the URL of a fork's tarball. This changes the install command shown in **Access** → **Computer** → **Link a computer**. When the value contains `pi-pocket-runner`, the command shown is `pi-pocket-runner`; else it is a whole Pi Pocket, and the command shown is `pi-pocket runner`.

**Its version.** The runner has its own version, apart from Pi Pocket's. It sends it to the server when it connects, and the computer's page in **Access** → **Settings** shows it.

## Who may use a computer

After the link, the runner trusts its server: the server already sends it every tool call, so a check on the computer would not stop a server that was broken into. Pi Pocket decides, with the same rules for linked computers and for **This server** (`src/server/access.ts`):

- **In charge.** The linker owns their runner. The owner of Pi Pocket owns **This server**. The owner may give **Link runners** to a user so they can link their own runner. Each computer's owner can turn on **Manage this computer** in a chosen user's **Permissions**, if the user is not limited to sessions. A manager is in charge of that computer alone. They see and prompt every session there, choose people, give folders, change settings, and set project trust. They cannot make other managers or take them off the computer. A manager does not become an admin. Their page names the computers they are in charge of. Sessions and tasks handed over still go to the owner of that computer. Only the owner of Pi Pocket and a linker in charge can unlink a runner. The owner of Pi Pocket lists a runner someone else linked to unlink it. They see no folders or sessions unless the linker chooses them, and have no charge unless the linker gives them **Manage this computer**. An unlinked runner's sessions stay and run nowhere. Only their starters and people they were shared with can read and archive them.
- **Blocked.** A linker who is made a viewer is in charge of nothing, and their computer is blocked until they are made a user again. Nothing starts there and nothing runs: a prompt, a change of settings, a `!` command, or a tool call in a session there is refused with the reason, each command the server was running there is cancelled, and the sessions' tasks (schedules, webhooks, watches) wait. Nobody is in charge of it meanwhile: nobody changes its people, folders, or settings, or allows anything there, and only the owner of Pi Pocket can unlink it. Its runner stays connected, and **Access** shows it as **Blocked**. A block takes nothing from anyone: its people keep their folders and keep seeing the sessions they saw, and its linker the sessions they started, to read. It is a rule, not a record: made a user again, the linker is in charge again and everything works at once. A background command already started on that computer is the computer's own process, and is not stopped.
- **The computer.** Who is in charge chooses the people who may use it. Nobody else can see its sessions, browse it, or start anything there. A person taken off it loses the sessions shared with them there in that same save, and does not get them back when chosen again: only what is shared with them anew. The server stopping in the middle changes nothing for them; the next start finishes what was left.
- **People and Computer.** Menu → **Access** has three views: **People**, **Computer**, and **Settings**. **Computer** is for users who are not limited to sessions and can use a computer or link one. A viewer has no **Computer** view. On a person's page, **Computers** lists where they work and what they have of yours. Tap a row that has a chevron to open **Computer** with just their column shown. If they are not yet chosen, turn on their switch under **People**. This is also how a runner's linker chooses someone from their page; there is no separate **Invite to your runner** button. Go back to **People** to see that person again. **Permissions** is still where you change what they may do and how they sign in. The part shown stays from one person to the next.
- **The grid.** **Group by** gives you **Folders** and **Sessions**, and **Projects** when you are in charge and the projects are known. Folders open to nested folders and their sessions; archived sessions are left out, and a worktree counts in the folder it came from. With one person shown, the folder row counts how many of its sessions they have. Most recently used sessions come first and keep their places while the rows are open. A folder or a project's cell shows the person's **Access** level (a project's is its top folder's). A level from a folder above is in italics. A disabled menu says why. A long name can be read from the row's title. Tap a session's name to close Access and open the session.
- **What the grid shows.** If you are in charge, the grid shows a column for each chosen person or person invited to a session there, **Project trust**, and the people switches below. **All folders** is the last row: open it to give a folder with no session in it. It reads only open folders, the same ones the picker shows (50 at a time, then **Show N more**). It is not shown during a search or filter, and an offline computer explains why it cannot list its folders. If you use someone else's computer, the grid shows only what the server tells you there for people with something you can change. It has no trust column, **All folders**, or use switches. If there is nothing to share, you get a note instead of a grid. A runner you can only unlink shows its name and a note, but no access details.
- **Search and filters.** **Search folders and sessions** looks for each word in the name or path, in any case. **Access** keeps sessions people have or do not have; **Last used by you** keeps them by when you last sent to Pi; **Started by** appears when more than one person started the sessions. A search opens the matching folders and shows the number of sessions found. **Clear** ends the search and filters; Escape clears the text. A session you just changed stays listed until the search changes. The **People** filter shows some columns, as “1 of 8 people.” The head and first column stay in view as the desktop grid scrolls. On a phone each row's name is above its cells; the people columns scroll sideways together.
- **Projects and trust.** A project is a git repository with its worktrees: the sessions there that are not archived name the projects, by the repository's top folder (a worktree counts for its main checkout), and a folder in no repository is in no project (`GET /api/runners/<id>/projects`, `this-server` too, for who is in charge of that computer; anyone else gets 404). The lookups reuse Memory's project cache, at most 4 at once. **Project trust** in the grid sets Pi's trust for the project's folders on that computer, in the same store and by the same code as a session's **Project trust** (`POST /api/runners/<id>/trust`, with `folders` and `choice`: `trust`, `trust-parent`, or `distrust`; 404 for anyone not in charge): **Trusted**, **Not trusted**, **Not decided** (with what Pi does then), or **Mixed** where its folders differ: its root, a worktree folder outside it, or a folder in it that someone decided for on its own (from a session there), each then on a row of its own. A choice on the project's row is saved for all of them. A trusted folder loads its own skills and model defaults in every session there, for everyone; a decision ends the trust requests of the sessions that wait in a folder it covers. An untrusted project row says that its own skills and model defaults stay off.
- **Folders.** Who is in charge gives each chosen person their folders on it. A user who shares what they were given there (**Share what they were given on \<computer>**, a switch of theirs in **Management**, off by default) also gives a folder that was given to them there, exactly as it was given, to someone who already prompts on that computer, and takes back only a folder they gave (`POST /api/runners/<id>/give`). Who uses a computer stays the choice of who is in charge of it. A given folder covers the folders inside it, by the path rules of that computer: on Linux and macOS only `/` parts folders, so a folder beside it whose name has a `\` in it (`proj\x` beside `proj`) is not inside it; on Windows `\` and `/` both do. Any other folder is refused: the folder picker shows only the given folders, and a person cannot ask for others. A folder is judged by where it really is, so a link in a given folder that leads out of it is outside it. A session is saved by the folder it really works in, on this server as on a runner: one started in, or moved to, a folder through a link is in the folder the link leads to, for who sees the sessions in a folder by its level and for whose it stays when folders change. A session saved by a link's path before this was so follows at the server's next start, and then its starter keeps it only if its real folder is theirs. A folder taken back, or all sessions in one turned off, takes effect in that same save; the sessions and tasks that go with it move a moment later, and the server stopping in the middle changes nothing: the next start finishes what was left. Changes to who is chosen and to folders go one at a time, and each is checked again where it is saved: a folder is given only by who may still give it there, to a person still chosen. A move to another folder, and removing a worktree, save where Pi works and the session's folder together, so a session is never judged by a folder it no longer works in. In the Files panel, the viewer, and attached files, a person reads the session's folder and their given folders; only who is in charge reads anything Pi can on the computer.
- **A folder's level.** Each folder row has one **Access** menu. Each item says in a line what the person gets. For a user: **No access**; **Start sessions**: they start sessions in it, and see their own and the ones shared with them; then three choices for the sessions others start in it, each with **Start sessions**: **Current sessions**: every session here now, whoever started it, and not the ones started later; **New sessions**: every session started here from now on, and not the ones here now; **All sessions**: every session here, the ones here now and the ones started later. A viewer has the same menu without **Start sessions**: **No access**, **Current sessions**, **New sessions**, **All sessions**. Open, the menu says the time of the level it has: **Up to** a date and time on **Current sessions**, **From** one on **New sessions**. A viewer reads such sessions and starts or prompts nothing. A user prompts them, as a session shared with them. It covers the folders inside it, and sessions in a git worktree that came from it. The record is the one of a user's folders: the folders given (`given`), the ones whose sessions they see (`sees`), for **Current sessions** a time per folder (`seesUntil`, milliseconds), by which they see only the sessions made at or before it, and for **New sessions** a time per folder (`seesFrom`, milliseconds), by which they see only the sessions made at or after it (`access.ts` `seesFolder`, which the session list, its live updates, opening a session by its id, and the tree all follow). **Current sessions** sets its time to when it is chosen, also from **All sessions**, so nothing that exists is hidden; **New sessions** sets its time to when it is chosen, so what exists leaves them, and the tasks they set up on those sessions go to who is in charge; each keeps its time when it is chosen again, and **All sessions** removes both. A folder in `sees` with no time (as saved before levels) is **All sessions**. Made a user or a viewer later, a person keeps each folder and its level; a former viewer has **Start sessions** with it. It is a rule, not a copy: **No access** removes the folder from both lists and its times in one save, as does taking them off the computer, and each task they set up on a session they leave goes to who is in charge of that computer. Sessions they started, and sessions shared with them one at a time, stay. A session moved out of the folder leaves them too, and each task they set up on it moves to who is in charge in the save of the move; moved to a folder inside it, or one they also see, it stays. Such a person shares the session on only with **Share what they were given** on for them, and does not renew its approval: that stays with its starter and who is in charge. Whoever gave a folder and is not in charge sets its level on their own page for that person while they still use that computer: **Start sessions** or **No access**, and the levels that show sessions only while they see every session in that folder themselves (**All sessions**: not **Current sessions** or **New sessions**) and share what they were given; a folder they were not given is not theirs to give (`POST /api/runners/<id>/level`, with `person`, `folder`, and `level`: `none`, `start`, `past` for **Current sessions**, `new` for **New sessions**, or `all`). No folder is refused for being special: the home folder, `/`, and the data folder can be given; a folder is refused only when it is not a real folder there.
- **Rights.** A chosen person who prompts has three more, each for that person on that computer alone, off until who is in charge turns it on. They are on a person's page in **People**, under **Permissions**: **Override take turns** and **Allow their own calls** in a group **On** with the computer's name, and **Share what they were given on \<computer>** in **Management**, after the managing permissions that hold everywhere. **Override take turns**: they take the wheel from someone who is driving a session there, hand it over for them, and turn take turns off under them, as who is in charge can. **Allow their own calls**: they allow their own `!` commands that Lancet Guard asks about there and, while **Approvals need someone else** is on, a risky call their own message led to; a call nobody is known to have asked for stays with who is in charge, and so does a `!` command someone else typed. **Share what they were given**: they share the sessions that are shared with them there, and the ones they access by a folder, and give a folder that was given to them there ([Sharing](#sharing)). On for them on one computer, it is not on on another; the owner needs it too on a runner someone else linked. A viewer, and a person invited to one session, get none of them. Such a permission ends when the person is no longer chosen for that computer, and is not back when they are chosen again; taking one back undoes nothing done with it (`POST /api/runners/<id>/rights`).
- **Approvals.** Each session has one approval. A person starting a session on a computer they are not in charge of approves it with a code from their own authenticator, which they link to their account (**Access** → their page), or waits for **Allow** from who is in charge, in Pi Pocket. Nothing is asked on the computer. Who is in charge is never asked on their own computer.
- **Time.** The approval lasts for the approval time of whoever used the session last, counted from that use: 7 days by default. The owner sets each person's time in **People**: 1, 7, 14, or 30 days, or never ends.
- **Locked.** When the approval ends, the session is locked: new messages, settings (a new name and a keep warm time too), and task changes wait until its starter's code, or **Allow** from who is in charge, renews it. Stopping work never waits: the run, a schedule, a pull request watch, a linked session, a queued message, turning keep warm off, archiving the session or bringing it back, or **Stop** in the Browser panel. An approval checks who a person is before Pi works for them; what runs on its own (a task, a linked session's report at the end of its run) asks nobody. A renewal is the session's: once it is renewed, everyone waiting on it goes on. Something given up while it waits is not made later. A message, a settings change, a task, or a new session is checked again at the moment it is saved: when the person lost the session, the wheel, the folder, or its approval while it was being prepared, nothing is saved.
- **Viewers** read sessions they may see and use the people chat; they never need a code. A viewer with a full account has the chat with one person (**Access** → their page → **Chat**) once the owner, or a user who manages users, turns on **Chat with one person** on their page (off until then); a temporary account, and a viewer invited to sessions only, never have it. They see no list of the people here: only their own page in **Access**, the names and pictures of the people in the sessions shown to them, and, with the chat, of the people they may chat with. With **Request access** on that page they ask whoever manages people for more. To prompt, a new viewer links an authenticator and is made a user with **Can prompt**, in **Access**. Removing a user's authenticator pauses them instead: they can only view until they link one again. They stay signed in. Their own page in **Access** says in red that it was removed, their row there reads **Relink**, and from that page they can still sign in another device, to link one there. Then their permissions come back automatically, and their schedules and pull request watch reports can go out again. A pull request watch that waited two weeks with nothing told ends, as any quiet watch does. If whoever manages them chooses **Keep as viewer**, they stay a viewer after linking. A viewer who linked a computer blocks it (**Blocked**, above). A viewer with a temporary account (what an invite makes unless it allows more) can do neither, until the owner turns **Allow viewer to become a user and prompt** on for them there. The invite's **Account expires in** sets how long the temporary account lasts after they join: 1 day, 1 week by default, 1 month, or **Never**. When it ends, the account and its session shares are removed, just as with **Remove person**. The owner or a user who manages them can change the end under **Account expires**; allowing them to become a user clears it.
- **A server from before these rules.** Before them, everyone not invited to one session had the whole server: a guest started sessions in any folder, prompted every session, and invited people; a viewer read every session. At its first start with the rules, such a server gives its people what they had (`config.ts` `keepAccess`, `app.ts` `#finishUpgrade`): each of them is chosen for **This server**; a guest is given the folder `/`, which holds every folder, and **Invite people**; and every session that is on this server then is shared with each of them. The sessions used in the last 7 days, and the ones a person was invited to alone, are approved by the owner, so the update itself locks nobody out. It is what they had, once, not a rule for what comes: a session started later is private unless its starter shares their new sessions with someone there ([Sharing](#sharing)), or the session itself is shared; a new session of a guest's is approved as any other. The owner takes any of it back as usual: the person's switch, their folder `/`, one session's **Revoke**. A person invited to one session keeps that session, and nothing changes for them. A server that had the rules already is left as it is: who was not chosen stays so (it is told by its file, `config.json` `access`, or by anything only the rules write there).

A person given a folder, including a viewer, can read and write its **Project** chat through a session they can see there. This includes the separate chats for folders inside it. Sharing a session alone does not give access to its folder's chat.

Approvals are listed nowhere. A locked session says **locked until allowed** on its row. Open the session to allow it again; there is no **Allow** on the row. Removing a person, taking them off a computer, or taking back a folder hands their sessions and tasks there to who is in charge (also the tasks they set up on sessions shared with them), in one save that a restart finishes; Pi then works for whoever has the session; nothing stops. A session that someone else moves out of the folders given to its starter follows the same rule in the save of the move: it and the tasks its starter set up on it go to who is in charge. Moved inside those folders, it stays theirs. A session that is no longer shared with a person follows the same rule: the tasks they set up on it (schedules, webhooks, watches, and the background commands Pi runs for them) go to who is in charge of its computer, the owner for **This server** and who linked a runner, in the save that ends the share; never to the session's starter. Who still has the session another way, by its folder or invited to it, keeps theirs.

Work under way runs to its end, with its subagents and linked sessions; an ended approval only stops what comes next. A copy, a move, or a linked session on the same computer inherits its source's approval. A copy to another computer is approved there as a new session is; where it is saved, its source must still be the person's to prompt, so a session taken from them while that approval waited is not copied. A session's own git worktree counts as the folder it came from, so a copy or a linked session that stays in it needs only that folder given. That holds only while the session works in its worktree: moved to another folder, it is judged by that folder, for who sees it and whose it is, though its worktree is still there to remove. Tasks that run on their own follow their session's approval only when the owner turns on **Tasks expire with the session**, under **Access** → **Settings** (then they run for 7 more days, with reminders, and pause). Ending an approval early (`DELETE /api/session-approvals/<session>`; the app has no button for it) locks people out at once, and the 7 days of its tasks count from then. A session that never had an approval counts from when the owner turned the switch on. A watch whose session is paused waits and is not counted as failing; it tells what it found once the session is renewed (a pull request watch gives up after two weeks with nothing told).

### What a session can reach on the computer

Each request from the server names its session and that session's folder. The runner refuses a request that names none, except the folder picker's listings. Each path in a request must be in the session's folder or below it, or in the session's own folders for its attached files, background task logs, browser downloads, and git worktrees (named by its permission id), or in the temporary folders the session made. Pi can also read, not change, its context files (`AGENTS.md`, `CLAUDE.md`) in the folders above, and the skills in `.agents/skills/` there and in your home folder. Commands run in the session's folder.

This is not a sandbox. A command still runs as you, and it can read and change files outside its folder. The runner's check catches a mistake on the server, not a server that was broken into.

## Continue a Pi session

Choose a computer in **New session**, then **Continue a Pi session…**. This lists Pi's terminal sessions on that computer. A continued session is a new Pocket session that runs on the same computer; Pi's original file is never changed.

On **This server**, only the owner and users who manage this server can list, preview, or continue Pi's terminal sessions. The new session gets an approval in its folder without asking.

On a linked computer, the server and runner work as follows:

| Step     | The server gets                                                                 | Who decides                                              |
| -------- | ------------------------------------------------------------------------------- | -------------------------------------------------------- |
| List     | For each Pi session: path, Pi's session id, title, cwd, modified, message count | The server: people who may start sessions there          |
| Search   | A filter on title and cwd only, done on the server over the list                | The server, over the list                                |
| Preview  | That one session's model and last messages, as in a local preview               | The server: people who may start sessions there          |
| Continue | That one session file                                                           | The server: a new session in its folder, approved as any |

The title is Pi's name for the session, or the first line of its first message, up to 80 characters. Only people who may start sessions on that computer get the list or a preview, and only of Pi's sessions in the folders given to them there; whoever is in charge sees all of them. The list marks a Pi session already continued only when that Pocket session is one they may see. Continue is a new session in the Pi session's folder: that folder must be one given to them, and it is approved as any new session is (their own code, or whoever is in charge of the computer).

The runner looks in `PI_CODING_AGENT_SESSION_DIR`, then Pi's `sessionDir` setting, then Pi's default session folder. The list has at most 300 sessions, newest first, and is cached for 5 seconds. Preview and continue check Pi's list afresh. The runner opens only a Pi file whose folder is in the new session's folder, and lets only that session read that one file for at most 5 minutes, never write it.

Files that extensions keep beside Pi's file come along too (with companion files, TannerMidd/pi-pocket#262), for example Billion Context's `.acp.json`. With the Pi file, Pocket names the suffixes the extensions here registered. The runner allows the session to read each of those that exists beside the file, the same way, and no other. Pocket reads each one, gives the extension a copy on the server, and removes the copy when the extension is done. A companion that cannot be read stays behind, and the session still opens. Runners from before this change allow only the Pi file, so nothing comes along.

## Programs that run the runner

A program that runs the runner, such as the desktop app, starts it with `pi-pocket runner start --confirm-via stdio` (or `pi-pocket-runner start --confirm-via stdio`).

The runner says when sessions work on the computer, for a tray icon, keeping the computer awake, or a warning on quit. It writes a line `PI-POCKET-ACTIVITY` and a JSON object, `{ "working": true, "folders": ["/Users/me/project"] }`, each time the state changes. The first line comes when work starts, so a program that saw none can take the runner as idle.

- `working`: sessions use this computer now.
- `folders`: the real folders of those sessions, sorted. Empty when `working` is false.

A file or command request of a session counts from when the runner sends it to the computer's tool process until its result, so a long command counts all the time it runs. Folder listings for the folder picker, file watches, and the browser's network connections do not count. The line says nothing about the commands, tools, or sessions themselves.

The state is smoothed, so short requests do not make it flicker. A folder shows after its work lasted 0.5 s, and stays 5 s after its last request ended, so the requests of one turn show as one stretch of work. When the runner stops, it writes a last line with `working` false if it was working.

## Runner settings in Pi Pocket

Each computer has a page in Menu → **Access** → **Settings**, for who is in charge of it: how long each person's approvals last, these settings, its tools, **Link again**, and **Unlink**. **This server**'s page has who is in charge, the approval times, its **Downloads folder**, and its tools (whether git and GitHub are ready on this server, checked when the page asks and kept for a minute). Its network is its own machine's, so it has no network switch, and it is never linked, so it has no plain HTTP line, key, **Link again**, or **Unlink**. A runner's page has:

- **Share the network with browsers** (on by default): see [The browser](#the-browser).
- **Downloads folder**: where browser downloads go on the computer.
- **Plain HTTP**: shown only. It is set on the computer, when it links ([Plain HTTP](#plain-http)).

The server sends a change to the runner at once, and again each time it connects. Nothing is saved on the computer but the link.

## Plain HTTP

The link encrypts every command (see [Secure link](#secure-link)), but the runner still uses HTTPS. It allows plain HTTP only:

- To this computer (`localhost`, `127.x`).
- To a device on your tailnet. The runner asks Tailscale itself (`tailscale whois`), so an address that only looks like a Tailscale address is not enough. Tailscale encrypts the traffic.

To link a server on another plain HTTP address, choose **Allow plain HTTP** when the runner asks, or add `--allow-http` to `pi-pocket-runner link`. Do this only on a network you trust. The choice is saved with the link.

## What works in a session

In Menu → **Access** → **Computer**, choose an online computer, then **New session**, then choose a folder on it. The session's title, top bar, and Pi's system prompt identify the computer. The fork sheet's **Computer** row lists only computers where you may start sessions. It starts on the session's computer if you may start there, or on the first one where you may start. You do not need permission to start on This server to fork on a runner. The Fork button waits for the destination folder. If you cannot start on any computer, the sheet disables Fork and says why. A copy can go from this server to a linked computer, back, or from one linked computer to another. A copy on a linked computer runs with that computer's list of extensions; a copy back on this server gets all extensions again. Pi gets a note with the new computer and folder, because paths earlier in the conversation were on the old ones.

Pi's `read`, `write`, `edit`, and `bash` tools run on that computer through Earendil's [pi-env](https://www.npmjs.com/package/@earendil-works/pi-env). They work as they do on the server. Goals, plans, questions, schedules, codemode, memory, PR watches, and [the browser](#the-browser) also work. Subagents and linked sessions that a session on a computer starts run on the same computer. A linked session in another folder needs that folder's approval, as a new session does.

Lessons stay with each project on its own computer; worktrees of that project share them. In **Memory**, **From …** sections offer approved lessons from other copies of the same GitHub repository. Choose **Add** to save one in this project; they never apply here automatically. PR watches read the origin and current branch on the linked computer, but poll GitHub from the server with the server's `gh` sign-in, not the computer's.

The runner checks git, the GitHub CLI (`gh`), and its GitHub sign-in when it starts and reconnects. **Access** and `pi-pocket-runner status` show whether git and GitHub are ready, with an install command or `gh auth login` when needed. A computer without them still works.

These also work, on that computer:

- The **Files** and **Changes** panels, the branch list, and **Show in the file manager** (it opens there).
- **Git worktree** in the new-session and fork sheets. The worktree is made on that computer at `~/.pi-pocket/worktrees/<permission id>/<name>`, with a new branch, uncommitted changes, and up to 50 MiB of new files; ignored files stay out. A worktree keeps its session's permission, and a fork gets its own. Removing the worktree removes its folder there; its branch stays, as on the server. The session's folder must include the repository root, because git writes there.
- The folder's project context files (`AGENTS.md`, `CLAUDE.md`) and the skills there and in that computer's home folder. Project trust is kept for each computer, and whoever is in charge of the computer decides it: its linker, not the server's owner. Lancet Guard works the same way there: the linker's own `!` commands run unchecked and they can allow a call their own message led to, while everyone else's, the owner's included, are checked as a guest's are on this server.
- Files mentioned with `@`, read on that computer.
- Attachments: each is copied to `pi-pocket-uploads/<session>/` in that computer's temporary folder when the message is sent, and the message gives that path. `<session>` is the session's permission id on that computer, so a session reaches only its own attached files. The system can clear its temporary folder when the computer restarts: move a file you want to keep out of it.

Artifacts read their `path` and asset files on the session's computer, then keep the published bundle on the server. Automatic design-system attachments are not available there: give their files in `assets`. Images opened from that computer, or written with `write` or `edit`, are kept in the session's uploads for offline viewing (25 MiB per image, 500 MiB per session; the oldest copies are removed above that).

Background tasks run on the computer in the session's folder, on Linux, macOS, and Windows. The runner owns each task through a separate child process, not through the pi-env tool process. A network drop, a server restart, or a tool-process restart does not stop tasks. When the runner stops or crashes, its task processes stop too: on Linux and macOS, the task's process group gets a polite signal, then a forced stop after 5 seconds. On Windows, the host uses `taskkill /T /F`; a Windows Job Object also stops the process tree if the host dies. If the computer cannot set up that Job Object, the task does not start, with an error that says why: without it, a task could outlive the runner.

The shell's exit code is final when the shell ends, even if a descendant redirected its output and keeps running. The task host stays registered while the task's process group or Windows Job Object has processes left. The runner's task list marks that task with `ended: true`, and signals still reach its descendants. Linux and macOS hosts check the group about once a second. If Windows cannot inspect the remaining processes, the host stays until the runner stops. A process that leaves its group with `setsid` on Linux or macOS is outside the runner's reach.

Their logs and exit codes stay in `<temp>/pi-pocket-tasks/<permission id>/` on that computer, reachable only by their session. Running now and the log view read them there, with the same output limits as local tasks. While the computer is offline, its watch waits, then checks again when it reconnects. Completed output and exit codes reach the session when it is back. The runner checks that the command's folder is in the session's folder before it starts a task. On Linux and macOS, commands use Bash, or `sh` if Bash is absent. On Windows, they use an installed Bash (not the Windows WSL launcher), or `cmd.exe` if Bash is absent. Temporary files can disappear when the computer restarts.

**Session cleanup** works for a session on another computer too. Its worktree is checked and removed on that computer, and its background tasks are stopped there, with their logs and exit codes. This happens only while the computer is online and not blocked, and the session's approval is live for the person doing the cleanup; otherwise the session stays, and the confirm says why. A cleanup never asks anyone to renew an approval. A worktree on another computer counts as 0 bytes: its size is not read. When the computer is no longer linked, or the person who started the session may no longer use it, the session can still be removed; what it has on that computer stays there, and its unfinished tasks are recorded as lost. Only people in charge of a session's computer can clean it up. The plan leaves a session out if it is on a different computer, even if the person can see it.

A project's own `.pi/settings.json` and prompt templates on that computer are not read.

### Extensions

A session on another computer runs with the built-in extensions that work there, and with the drop-ins that say they do. A drop-in says so with one line in its module:

```ts
export const remoteSessions = true;
```

Other drop-ins load only in sessions on the server. A drop-in that the owner turns on or off, or that changes the line, is added to or taken out of every session on another computer, existing ones too.

The line is a promise by the module's author: its tools reach the session's files and commands only through the session (`api.env`), which is that computer's. What the module itself does with Node (`node:fs`, `node:child_process`) runs on the server, in the server's folders. A module that only works on the conversation (its history, compaction, prompts, models) needs nothing more.

## The browser

The browser tool and the **Browser** panel work in a session on another computer. Chromium runs on the server, but every connection of its pages goes out from the linked computer:

- `localhost:5173` is the linked computer's port 5173. The Browser panel lists the ports that the computer listens on (`lsof` on macOS, `/proc/net/tcp` or `ss` on Linux, `netstat` on Windows).
- Names resolve with the computer's DNS, and pages use its routes, VPN, and local network. Sites see the computer's IP address.
- Pi's model calls do not change: they go out from the server.
- File paths and `file://` addresses do not open, because the browser would read the server's disk. Serve the files instead, for example with `python3 -m http.server`.

How it works: these pages use a second Chromium on the server, with a proxy built into Pi Pocket. Each session's pages have their own proxy credentials, which name the computer. The proxy sends each connection to the runner over its link, and the runner opens the TCP connection on the computer. Chromium's own background traffic and anything without valid credentials go to a proxy that refuses everything. WebRTC sends no UDP outside the proxy, and QUIC is off. If the computer is offline, the page fails with "<name> is offline". Nothing goes out from the server.

To stop sharing the network, turn off **Share the network with browsers** on the computer's page in **Access** → **Settings**. The runner then refuses every connection, and pages show "<name> does not share its network". The change takes effect at once.

The risk: pages in the browser of a session on a computer can reach that computer's network (its `localhost`, the home network, a tailnet, a VPN) like any program on it. This is part of the risk of a runner. Pi and anyone who can steer the session's Browser panel can open such pages. Link only a server you trust, and turn off network sharing if the computer must not do this. Other programs on the server cannot use the proxy, because they do not have the credentials.

**Downloads.** A file that a page downloads goes to the computer's temporary folder, in `pi-pocket-downloads/<session>/` (on macOS, the per-user `$TMPDIR`, not `/tmp`). `<session>` is the session's permission id on that computer: each session has its own folder, and the runner lets a session reach only its own, never another session's. The system can clear its temporary folder when the computer restarts, so move a file you want to keep out of it. To use another folder, set **Downloads folder** on the computer's page in **Access** → **Settings**. The files then go to `<folder>/<session>/`, and a session reaches only its own `<session>` folder there: the chosen folder itself, and anything else in it, stays out of reach. Clearing it returns to the temporary folder. The tool result gives the full path and the size. If the name is already used, the file gets a number, such as `report (2).pdf`. The bytes pass through the server: Chromium saves the file in the server's private temporary folder, Pi Pocket sends it over the runner link to the computer in parts, and then the server deletes its copy at once, also when the copy fails. Downloads larger than 2 GiB fail. In a session on the server, downloads go to `pi-pocket-downloads-<uid>/<session id>/` in the server's temporary folder. Only the server's user can open this folder (mode 0700). Pi Pocket refuses the folder if another user owns it or if it is a link. To use another folder on the server, set **Downloads folder** on **This server**'s page in **Access** → **Settings**, as an absolute path on the server: the files then go to `<folder>/<session id>/`. Clearing it returns to the temporary folder.

**macOS desktop app.** On macOS 15 and later, connections to devices on the local network (not `localhost`) can need the **Local Network** permission. The desktop app runs the runner as a child process, so macOS can ask for this permission on behalf of the app. The app's `Info.plist` does not have an `NSLocalNetworkUsageDescription` yet, so the system prompt has no explanation. If pages on the local network fail with "No route to host", allow Pi Pocket in System Settings → Privacy & Security → Local Network. This was not tested on a Mac.

## Sharing

The people chosen in Menu → **Access** can start sessions on it, in their given folders, including forks. Their sessions run as the computer's user, with the same access to its files and commands. Who is in charge of it alone changes its settings and who may use it. Sharing does not change this rule.

By default, a session on a linked computer is private to its creator. Other people cannot see it in their session list, open it, prompt it, or fork it. Who is in charge of the computer sees every session on it, and so does a person with a folder at **All sessions** (or at **Current sessions**, the sessions made up to then; or at **New sessions**, the sessions made from then on) ([Who may use a computer](#who-may-use-a-computer)). These access rules also protect a private session's forks and subagents.

The session's starter, or who is in charge, shares it one person at a time, with people who may use its computer. Someone it is shared with shares it on only with **Share what they were given** on for them on that computer (its switch is on their page in **Access** → **People**, under **Permissions**, in **Management**; off by default). Whoever is in charge of the computer turns it on: then they share the sessions that are shared with them there, and the ones they access by a folder. On for them on one computer, it is not on on another. Nobody shares what they do not have. The owner is no one special on a runner someone else linked: they share on a session that is shared with them there, and give a folder that was given to them there, only once its linker turns the switch on for them, and then only to the people its linker chose. With it on, an invite link to such a session, which takes **Invite people** as well, brings in a viewer held to that one session, whom its linker did not choose. A **Custom** invite (Menu → **Access** → **Invite someone** → **Share**) gives the sessions its maker checks, on any computer, and only the ones they may share there: when it is made, and again when someone joins with it. People it is shared with can prompt it, and its commands run on the linked computer for them too.

A share is taken back by whoever made it (while they still have the session), by the session's starter, and by who is in charge. In **Share**, a person someone else shared it with is ticked and greyed out for anyone who cannot take that share back. What someone shared stays when they lose the session or that permission: its starter, or who is in charge, takes it back. Taking someone off the share list closes the session in their tabs at once.

To share with one person, open Menu → **Access** → **People**, choose that person, and tap a computer under **Computers**. You can also open its grid directly in **Computer**. Find the session and use **Invite** in their column. It shares that session at once without changing anyone else's share. **Revoke** asks before taking a share or a one-session invite back. A share you cannot take back says **Shared**, with the giver in its title when known. A session they have **Through folder** can be invited separately with the plus button, so they keep it if the folder is taken away. Taking a share back does not take away access they still have through a folder.

With one person shown, **Select** adds a checkbox to each session and to each folder or project's listed sessions. **Select all** checks the sessions that are shown. **Share (N)** or **Revoke (N)** changes those that the button can change in one request (up to 500 sessions; `POST /api/users/:id/sharing`). **Revoke** asks once, says how many sessions the person started move to who is in charge with their tasks, and how many they keep through a folder. One notice says how many changes the server refused and why. **Done**, a new computer, or a change to the people shown ends Select. A selection is for one person on one computer; to share on two computers, do it on each. A session the person started has no **Revoke** on its row; use Select and **Revoke** instead.

A computer someone else is in charge of uses `GET /api/runners/:id/sharing` for its grid (`this-server` works too). When you have **Share what they were given** there, a folder's level menu gives a folder you were given or takes back one you gave. A folder someone else gave them shows the giver in its title and cannot be changed by you. The person's **Computers** page counts your sessions and folders they have. A row can say they are in charge, cannot use the computer, or are invited to a named session, without opening a grid.

To share sessions you start from now on, open the other person's page in Menu → **Access** → **People**. Under **Computers** → **New sessions**, turn on **Share my new sessions on** for one computer. It is off by default. You can turn it on if you can start sessions there and the person can use that computer. Someone in charge already has every session there, and someone invited to one session only cannot get new ones this way. The switch shares only sessions you start on that computer, and changes no existing session. Taking either person off the computer clears the switch; choosing them again does not turn it back on. For one person and one folder, with the sessions already there, set that folder's **Access** to **All sessions**.

This server follows the same rules, as **This server** in Menu → **Access** (`src/server/access.ts` holds the one policy for both).

## When the computer is offline

Offline is offline. While a linked computer is offline, its sessions are offline too: there is no grace period, and nothing fails because the computer is away. The server keeps the link's work and waits. The session shows "<computer> offline, reconnecting…", and its mark in the session list is dimmed.

| What happens                                             | What happens to the work                                                                                                                                            |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The connection drops, for any length of time             | Nothing is lost. Commands keep running on the computer. Their output arrives when the runner reconnects, and the session continues where it stopped.                |
| A tool call, or a message, while the computer is offline | It waits for the computer. Attached files are copied there when it is back. **Stop** ends the wait.                                                                 |
| The runner quits, or the computer restarts               | Commands and runner-owned background tasks stop. Commands come back as interrupted; task logs and exit codes remain. The session continues when the runner is back. |
| The server restarts                                      | Running commands return as interrupted. Background tasks keep running on the computer, and the session picks up their output when the runner reconnects.            |

The quiet limit of commands (a bash command that prints nothing for 15 minutes is stopped) applies on a linked computer too. Time the computer is offline does not count toward it.

Panels that show the computer's files (Files, Changes, the folder picker) say that the computer is offline instead of waiting. A new session, a fork, or a move to another folder on an offline computer cannot start.

Unlinking a computer in **Access** stops its runner and cancels its key. A runner that the server removed exits with code 3, except in macOS service mode, where it exits with code 0 so launchd does not restart it. The desktop app does not restart it. The runner stops the same way when its computer is linked again with a new key, when another runner takes its link, or when the two sides speak different link protocols.
